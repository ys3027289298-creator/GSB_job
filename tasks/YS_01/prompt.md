请直接在当前文件夹中创建并完成一个可以在浏览器中运行的原创桥梁应急检修调度游戏。所有代码、配置、测试和说明都必须写入当前文件夹，不要创建嵌套项目目录，也不要只在聊天中输出代码。游戏名称为《桥梁应急检修：值班班次》。
一、技术要求
1. 使用 React 与 TypeScript 开发。
2. 使用 Vite 作为项目构建工具，开发服务器必须使用启动器注入的独立端口 `GSB_PORT`，禁止使用 3000，不要把端口写死，也不能占用其他任务正在使用的端口。
3. 使用 HTML、CSS 和 SVG 或 Canvas 制作可缩放、可平移的桥梁结构图、车道、桥墩、检修点、施工区域和交通流。
4. 使用 TypeScript 实现任务前置关系、资源占用、时间推进、交通压力、风险结算、事故判定、撤销边界、得分和存档逻辑。
5. 使用 Vitest 编写核心逻辑测试，并提供可直接运行的测试脚本。
6. 使用浏览器 localStorage 保存当前班次、设置、解锁内容和最近一次结算，不需要后端服务。
7. 安装依赖后即可在浏览器中运行，不能依赖远程 API、登录、云数据库或外部服务。
8. 使用原创的几何图形、颜色、图标和占位音效，不使用商业游戏、商业软件或真实厂商的角色、名称、模型和素材。
9. README 必须说明安装、启动、测试、操作和项目结构。
10. 所有代码、配置、测试和说明直接放在当前文件夹根目录，不要再创建项目子目录。
二、游戏目标
1. 玩家担任桥梁夜间应急检修班次调度员，在有限的 45 分钟检修窗口内处理多处故障。
2. 故障包括桥面裂缝、伸缩缝卡滞、照明线路故障、排水堵塞、护栏损伤和桥墩检测异常。
3. 每项检修都需要满足前置任务、工种、设备、封道范围和预计工时，不能通过随意点击直接完成。
4. 检修队、吊装设备、检测仪器、维修材料和预算都是有限资源，不能同时被两个任务占用。
5. 玩家必须在交通压力、事故风险、任务优先级、施工安全和剩余时间之间做出取舍。
6. 游戏单局应在十到十五分钟内完成，允许玩家暂停、逐分钟推进、重新开始并查看班次结算。
7. 所有结果必须来自真实的状态计算，不能用固定演示动画或预先写死的胜负结果。
三、启动与菜单
1. 启动后显示标题页，提供开始班次、继续班次、班次记录、操作说明、设置和清除本地存档入口。
2. 点击开始班次后可以快速进入第一阶段，不得要求注册、登录或复杂配置。
3. 继续班次必须读取 localStorage 并恢复故障状态、时间、资源、风险、事件记录和当前选择。
4. 提供暂停、继续、重新开始班次、返回主菜单和放弃当前班次按钮。
5. 清除存档必须有二次确认，不能误触后直接删除所有进度。
6. 设置至少包括音效开关、动画强度、颜色辅助模式和是否显示操作提示，并且刷新后仍然保留。
四、班次控制与时间系统
1. 页面必须有明确的当前时间、剩余检修窗口和时间推进状态。
2. 玩家可以暂停时间、恢复时间、逐分钟推进和快速推进到下一个关键事件。
3. 未暂停时，交通压力和部分风险会随时间持续计算，不能只在玩家点击按钮时变化。
4. 每次推进时间都要处理任务进度、资源占用、交通流、天气或突发事件和事故判定。
5. 任务开始后需要锁定预计工时，已经执行的时间不能通过普通撤销回退。
6. 只能撤销尚未开始执行的调度计划，已经开始的施工、已经发生的事故和已经完成的检测结果不能撤销。
7. 班次结束时自动进入结算，剩余时间为零或桥梁关键安全指标达到失败阈值时显示失败原因。
五、桥梁结构图与场景
1. 中央区域必须显示可缩放、可平移的桥梁结构图，而不是普通表格或静态背景图。
2. 桥梁图至少包含双向车道、中央隔离带、三个桥墩、两个伸缩缝、照明点、排水口、护栏、检修点和入口出口。
3. 每个检修点显示当前状态、故障类型、风险等级、已分配队伍和封闭范围。
4. 施工区域要在图上用颜色和纹理显示，封闭车道、缓冲区、警示区和可通行区域必须能区分。
5. 图上要显示简化的交通流，封闭车道后车辆密度、速度和排队长度要真实变化。
6. 支持鼠标滚轮缩放、拖拽平移、点击检修点查看详情和点击车道查看封道计划。
7. 需要提供缩放到全桥、聚焦当前任务和恢复默认视图的按钮。
8. 大型结构、施工区域和交通对象必须有合理的几何边界，不能出现明显重叠或点击错位。
六、故障与检修任务系统
1. 至少实现六类故障：桥面裂缝、伸缩缝卡滞、照明线路故障、排水堵塞、护栏损伤和桥墩检测异常。
2. 每个任务必须拥有唯一编号、位置、前置任务、所需工种、所需设备、材料消耗、预计工时、风险等级和完成条件。
3. 任务至少包含待处理、已计划、施工中、待验收、已完成、已取消和失败状态。
4. 裂缝任务需要先检测再封道和灌补，检测结果会影响最终工时和材料消耗。
5. 伸缩缝任务需要吊装设备和交通管制，未完成相邻区域隔离时不能开工。
6. 照明线路任务需要电气队和检测仪器，施工期间对应区域必须降低交通速度。
7. 排水堵塞任务需要先确认积水范围，暴雨事件发生时未处理区域会增加风险。
8. 护栏损伤任务需要临时防护和维修材料，未设置隔离时不能完成验收。
9. 桥墩检测任务需要潜在风险标记，检测发现异常后必须解锁后续加固或限行方案。
10. 每个任务的按钮都要根据当前资源、前置条件和时间状态启用或禁用，并显示不能执行的具体原因。
七、队伍、设备与资源
1. 至少提供道路施工队、电气维修队、结构检测队和吊装队四种队伍。
2. 每支队伍拥有位置、可用状态、专业能力、施工速度和当前任务。
3. 至少提供检测仪器、吊装设备、切割设备、照明设备、防撞车和临时隔离栏六类设备。
4. 队伍和设备不能同时分配给两个施工任务，分配冲突必须被规则引擎拦截。
5. 资源至少包括预算、维修材料、燃料或车辆调度额度、剩余工时和应急备用金。
6. 维修材料、设备占用和预算变化必须由真实任务状态计算，不能只修改界面数字。
7. 玩家可以在班次中调整未开工任务的队伍、设备、开始时间和封道范围。
8. 资源不足时显示清楚的缺口和可行替代方案，例如延迟任务、缩小施工范围或调用备用设备。
八、交通、封道与安全风险
1. 每条车道必须拥有当前通行状态、车流量、平均速度和排队长度。
2. 封闭不同车道会改变交通压力、通行速度和事故风险，封闭范围越大不代表一定更安全。
3. 施工区必须设置缓冲区、警示区和隔离设施，否则施工期间会持续累积安全风险。
4. 未封道直接进行高风险任务时，可能触发车辆闯入、二次碰撞或任务中断。
5. 交通压力过高会导致桥面状态恶化、班次评分下降或新增紧急任务。
6. 玩家可以选择短时全封、单车道封闭、分时封闭和临时限速等方案，不同方案必须有不同的时间、预算和风险效果。
7. 风险必须分为交通风险、施工风险、结构风险和进度风险，并在界面上分别显示。
8. 风险达到阈值时要显示预警、倒计时和可采取的处理措施，而不是突然判定失败。
九、连续任务流程
1. 第一阶段为快速评估：确认至少四处故障、完成两次检测并确定优先级。
2. 第二阶段为安全布控：安排封道、设置隔离、处理照明和排水等影响施工安全的项目。
3. 第三阶段为集中检修：在有限资源下完成桥面裂缝、伸缩缝和护栏等主要维修任务。
4. 第四阶段为验收撤场：完成复检、撤除临时设施、恢复车道并处理剩余风险。
5. 每个阶段都必须有明确开始条件、完成条件、失败条件和屏幕提示。
6. 前一阶段的检测结果、事故和资源消耗必须影响后一阶段，不能每个阶段相互独立重置。
7. 至少设计三种结局：安全完成、带风险完成和班次失败，并显示具体原因。
十、动态事件
1. 至少实现六种动态事件：突发暴雨、车流激增、运输车辆故障、隔离设施移位、检测仪器异常和桥下水位上涨。
2. 动态事件不能只弹出文字，必须实际改变时间、路线、资源、交通压力、任务状态或风险。
3. 事件发生时显示事件来源、影响范围、倒计时和至少两种处理选项。
4. 处理选项必须产生不同结果，例如消耗预算换取备用设备、延迟任务换取更低事故风险或缩小封道范围换取更高施工风险。
5. 部分事件要根据之前的封道决策、检测结果、剩余资源和已完成任务触发。
6. 同一种初始数据和随机种子必须得到可复现的事件顺序，刷新后不能无故改变已发生事件。
十一、事件记录、撤销与存档
1. 每次调度、分配、封道、开工、暂停、完成、事故、检测和事件处理都必须写入事件记录。
2. 事件记录至少包含班次时间、事件类型、操作对象、执行者、状态变化、资源变化和结果说明。
3. 提供按时间排序的事件面板，并支持筛选任务、风险、资源和事故类型。
4. 尚未执行的调度计划允许撤销，已经消耗时间或产生结果的操作禁止撤销。
5. 刷新页面后必须恢复当前班次，而不是返回固定初始画面。
6. localStorage 数据需要有版本号和基础校验，损坏时显示可理解的恢复提示。
7. 提供保存成功提示、最近保存时间和手动保存按钮。
十二、计分、升级与结算
1. 结算至少统计完成任务数、任务优先级完成率、平均风险、事故次数、封道时长、预算使用、材料剩余、总用时和事件响应质量。
2. 评分需要同时考虑安全、效率、交通影响、资源管理和检修完整度，不能只按完成任务数量计算。
3. 安全完成可以解锁新的桥梁班次、设备或困难模式，带风险完成只能获得部分奖励。
4. 结算页面显示每项得分的来源和扣分原因，不能只显示一个总分。
5. 改装或解锁内容必须在下一次班次中真实影响队伍速度、设备能力、风险或资源上限。
6. 失败页面必须显示导致失败的事件链，并提供查看记录、重新开始和返回菜单按钮。
十三、界面要求
1. 顶部显示班次名称、当前阶段、剩余时间、暂停状态和保存状态。
2. 左侧显示阶段目标、待办任务、前置条件、预计工时和任务状态。
3. 中央显示可缩放桥梁图、交通流、检修点、封道区域、施工队伍和事件标记。
4. 右侧显示队伍、设备、预算、材料、交通压力、四类风险和当前选中任务详情。
5. 底部显示时间推进控制、撤销入口、封道方案、快速聚焦、事件记录和结束班次入口。
6. 任务详情必须显示可执行条件、缺少资源、冲突原因和预计结果。
7. 不同风险等级使用颜色、图标和文字同时表示，不能只依赖颜色。
8. 关键事件需要有明显但不遮挡主视图的提示，提示至少保持足够时间方便录屏。
9. 窄屏浏览器下必须保持主要操作可用，不能出现按钮完全不可点击或信息重叠。
十四、录屏与演示要求
1. 启动游戏后应在一分钟内进入第一阶段。
2. 提供一条十到十五分钟内可完成的推荐路线，路线必须包含检测、封道、资源冲突、动态事件、施工和验收。
3. 录屏中要能清楚看到玩家安排队伍、选择封道、推进时间、处理事件、查看风险和完成结算。
4. 演示必须至少展示一次非法并行施工被拦截、一次设备冲突提示、一次动态事件处理和一次任务撤销边界。
5. 不能使用自动播放代替玩家操作，不能将所有任务预先标记为完成。
6. 任务失败后可以一键重新开始，不能要求手动清理浏览器数据。
7. README 中提供推荐演示路线和关键操作说明。
十五、测试与完成标准
1. 为时间推进、暂停、逐分钟推进和班次结束编写 Vitest 测试。
2. 为任务前置条件、状态流转、任务工时和完成条件编写测试。
3. 为队伍占用、设备冲突、材料消耗、预算扣除和资源不足编写测试。
4. 为封道方案、交通压力、施工隔离和四类风险结算编写测试。
5. 为非法并行施工、未完成前置任务、重复占用设备和无隔离施工编写测试。
6. 为撤销未执行计划、禁止撤销已执行操作和事件记录编写测试。
7. 为随机种子复现、动态事件、事故判定和结局计算编写测试。
8. 为 localStorage 保存、刷新恢复、版本校验和损坏存档处理编写测试。
9. 为结算评分、奖励解锁、失败原因和重新开始编写测试。
10. 完成后实际运行全部测试，并修复失败用例。
11. 实际打开浏览器，完成一次检测、封道、分配队伍、推进时间、处理事件、施工和验收流程。
12. 实际完成一次安全完成流程和一次因风险或时间耗尽导致的失败流程。
13. 所有按钮、任务、资源、风险、事件、撤销、存档、结算和菜单功能都必须真正可用。
14. 不能留下空函数、假按钮、无效菜单、明显 TODO、固定胜负结果或只改变显示数字但不影响状态的功能。
15. 最后在 README 中说明项目结构、启动方式、操作方法、测试方法、存档规则和主要功能。
